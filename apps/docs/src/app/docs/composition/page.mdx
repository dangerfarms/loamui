# Composition

FarmUI components compose: they are built from parts, every part renders a sensible element by default, and one merge contract governs how your props combine with the component's wiring. Learn it once — it works the same everywhere.

## Parts and built-in elements

Compound components expose their anatomy as parts you assemble in JSX. Each part renders a real
element suited to its role (a `Popover.Trigger` is a FarmUI Button, a `Breadcrumbs.Item` is a
link), so the common case needs no ceremony at all:

```tsx
<Popover.Root>
  <Popover.Trigger>Open filters</Popover.Trigger>
  <Popover.Popup>
    <Popover.Title>Filters</Popover.Title>
    <Popover.Description>Narrow down the results.</Popover.Description>
    <Popover.Close>Done</Popover.Close>
  </Popover.Popup>
</Popover.Root>
```

Because the built-in trigger _is_ a Button, it adapts to its context like any Button; see the
[Contextualism guide](/docs/contextualism).

## Substituting elements with `render`

When you need a different element (your router's `Link`, a component of your own), pass it via
`render`. The part's wiring (ids, ARIA, handlers, anchor styles) merges onto the element you
provide:

```tsx
// Your framework's router link inside breadcrumbs
<Breadcrumbs.Item render={<Link href="/settings" />}>Settings</Breadcrumbs.Item>

// A SignpostLink that navigates client-side
<SignpostLink render={<Link href="/apply">Start your application</Link>} />

// Full control: a function receives the typed wiring props
<Popover.Trigger
  render={(props) => <MyFancyButton {...props} glow />}
/>
```

**`render` is never required.** It exists only to substitute the built-in element. If you find
yourself writing `render` for an everyday case, there is usually a simpler built-in form, or a gap
you should report.

A dedicated `render` prop keeps `children` unambiguous: always content, never secretly the
element. The function form gives you typed access to the wiring when you need it.

## The merge contract

When wiring merges onto your element, the rules are always the same:

- **Event handlers chain.** Your handler runs first, the component's wiring second. Both always
  run; neither can accidentally disable the other.
- **`className`s concatenate.** Yours and the component's both apply.
- **`style` merges, wiring wins on conflicts.** Wiring styles such as `anchorName` position the
  popup and are load-bearing; everything else of yours passes through.
- **ARIA id lists concatenate.** An existing `aria-describedby` on your element is kept and
  extended.
- **Refs compose.** Your ref and the component's both receive the node.
- **Everything else: your prop wins.**

## Styling open state

Parts expose their state as data attributes: the same vocabulary on every component, working
identically whether the browser renders the popup natively (top layer) or via the fallback path:

```css
/* Keep a trigger highlighted while its popup is open */
.toolbar [data-popup-open] {
  background: var(--fui-surface-hover);
}

/* Style the open panel */
.fui-Popover-popup[data-open] {
  border-color: var(--fui-primary);
}
```

## Form controls and Field

The text-like controls (`Input`, `Select`, `Textarea`, `Range`) are bare: compose them inside a
`Field` and they self-wire — id, described-by and invalid state all flow from context, with
`Field.Label`, `Field.Description` and `Field.Error` as the parts:

```tsx
<Field.Root>
  <Field.Label>Email</Field.Label>
  <Field.Description>We'll only use this to reply.</Field.Description>
  <Field.Error>{error}</Field.Error>
  <Input type="email" />
</Field.Root>
```

Inline controls (`Checkbox`, `Switch`, `Radio`) keep a labelled convenience form
(`<Checkbox label="…" />`) because their anatomy is a row; their bare parts (`CheckboxControl`,
`SwitchControl`, …) compose inside a `Field` the same way. For an arbitrary element of your own,
`Field.Control render={…}` wires the same props onto it:

```tsx
<Field.Root>
  <Field.Label>
    <SwitchControl defaultChecked /> Email notifications
  </Field.Label>
  <Field.Description>Sent at most once a day.</Field.Description>
</Field.Root>
```
